1. Introduction & Core Architecture

Welcome to our developer-first REST API. Our architecture is designed to allow you to accept zero-commission UPI payments with absolute enterprise reliability.

The API is organized around REST, accepts application/json encoded requests, returns JSON-encoded responses, and utilizes standard HTTP response codes.

Authentication

All endpoints are authenticated using your secret key. You must pass this key in the header X-Fam-Key for every request. If omitted or invalid, the API returns 401 Unauthorized.

2. Distributed Systems Reliability: Idempotency

In the context of financial technology, the public internet is fundamentally unreliable. Connections drop, routing tables update, and timeouts occur. Because HTTP POST requests are not inherently idempotent, a naive client retry after a timeout could result in a duplicate payment.

To resolve this, we highly recommend architecting your integration to utilize Idempotency. While our API creates unique sessions per request, you should strictly map your internal order_id to exactly one payment creation attempt. If a network timeout occurs, you should query the /check-status endpoint using your order_id before attempting to create a new order.

POST

/api/create-order

Creates a payment session, returning a hosted checkout URL where the user can scan a dynamically generated UPI QR code.

Request Body Parameters

Parameter Type Required Description
amount Float YES The exact payment amount in INR (e.g., 499.00).
order_id String OPTIONAL Your system's unique identifier for this order. Highly recommended for idempotency.
customer_mobile String OPTIONAL Customer's 10-digit mobile number.
callback_url String OPTIONAL The webhook URL we will POST to upon successful payment.

    "amount": "100.00",
    "order_id": "ORD_20260914_7702",
    "customer_mobile": "9999999999",
    "callback_url": "https://yourwebsite.com/webhook"
  }'

Cryptographic Webhook Security

UPI transactions rely on asynchronous banking switches. Therefore, you must rely on webhooks for finality. Do not fulfill orders based solely on synchronous redirects.

When a payment completes, we transmit a POST request to your callback_url. To prevent forged requests, we cryptographically sign every payload using HMAC-SHA256.

The signature is transmitted in the X-FamGateway-Signature header. You must reconstruct the HMAC hash using your Secret API Key and compare it using a constant-time equality function.

# Python Verification Example
import hmac, hashlib

def verify_webhook(raw_payload_body, header_signature, api_key):
    expected_signature = hmac.new(
        api_key.encode(), 
        raw_payload_body, 
        hashlib.sha256
    ).hexdigest()
    
    return hmac.compare_digest(expected_signature, header_signature)

6. Standardized Error Handling

Our API adheres to standard HTTP error reporting syntax, categorizing responses into 2xx for success, 4xx for client faults, and 5xx for server issues.

HTTP Status Reason Phrase Application Context
200 / 201 OK / Created Successful execution of the API action.
400 Bad Request Malformed syntax or omission of mandatory parameters.
401 Unauthorized The API Key is missing, expired, or invalid.
429 Too Many Requests You have exceeded your allocated API rate limiting threshold.
500 / 502 Server Error An unexpected anomaly or invalid response from upstream banking partners.

UPI-Specific Decline Codes

You may encounter these codes when a transaction fails at the NPCI or Issuing Bank level:

UPI Error Description
U30 Insufficient Funds in customer's bank account.
U16 Risk Threshold Exceeded (daily limits breached).
PIN Error User entered an incorrect UPI PIN.
